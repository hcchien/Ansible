# Private Board Encryption Protocol v1

Status: implementation draft; cryptographic review required before production
enablement.

## Constitution Review

This protocol follows the Tris-Aura engineering constitution:

- the Forum Host and Relay are transport and policy boundaries, not key owners;
- plaintext and board epoch keys remain on authorized user devices;
- revocation prevents future access but never deletes local plaintext or claims
  that previously disclosed plaintext can be recovered;
- each board uses unlinkable device key material and board-scoped capabilities;
- AppView, public search, previews, analytics, and federation never receive
  private-board plaintext;
- unsupported custody, unknown protocol versions, stale policy versions, and
  missing epochs fail closed.

The compliance review's hardware-custody and confidential-content gaps are
therefore release gates. The feature must remain disabled in production until
an external cryptographic review accepts this protocol and implementation.

## Threat model

The protocol protects content when the Relay, Forum Host database, object
storage, CDN, backups, or their operators are compromised. It does not protect
content from an authorized member device, screenshots, malicious endpoint
software, or a member who retained an earlier epoch key.

The Host may learn routing metadata needed to enforce policy: opaque board ID,
record ID, ciphertext size, epoch number, timestamps, and a board-scoped
capability subject. It must not receive titles, bodies, attachment names,
notification text, full VCs, global holder identifiers, or plaintext keys.

## Keys

### Board epoch key (BEK)

- 256 random bits generated by an authorized board administrator device.
- One key per monotonically increasing `epoch`.
- Stored locally using OS protected storage; never sent to the Host in
  plaintext.
- Rotated after member/device removal, administrator-requested compromise
  response, or a policy version that changes confidentiality membership.

### Board device key (BDK)

- P-256 ECDH private key generated in Secure Enclave, Android StrongBox/TEE,
  or an explicitly supported desktop hardware keystore.
- Unique per board and device. Alias:
  `elix.board.content-ecdh.v1.<sha256(board_id)>`.
- Private bytes are non-exportable. Signing keys are never reused for ECDH.
- Devices that report `reduced_trust` cannot join an encrypted board.

## Epoch key envelope

An administrator device wraps a BEK independently for every authorized BDK:

1. The wrapping administrator selects its board-scoped hardware BDK as the
   sender key.
2. Derive `Z = ECDH(sender_bdk_private, recipient_bdk_public)` inside the
   sender hardware keystore. The recipient derives the same value with its
   hardware BDK and the authenticated sender public key.
3. Derive `KEK = HKDF-SHA-256(Z, salt=SHA-256(board_id || epoch),
   info="elix-private-board-key-wrap-v1", length=32)`.
4. Encrypt the 32-byte BEK with AES-256-GCM and a random 96-bit nonce.
5. Authenticate canonical AAD containing `version`, `board_id`, `epoch`,
   `recipient_device_key_id`, `recipient_public_key_hash`, and
   `policy_version`.
6. Upload only the envelope, sender board-scoped public key, nonce,
   ciphertext, tag, and AAD digest to the Host.

The recipient performs hardware ECDH using its non-exportable BDK, derives the
same epoch-specific KEK, verifies AAD/tag, and stores the BEK in OS protected
storage. A unique HKDF salt per board and epoch prevents KEK reuse even though
the device pair remains stable within a board.

## Content envelope

Every thread, post, reply, and attachment manifest is serialized as canonical
UTF-8 JSON and encrypted independently:

- AEAD: AES-256-GCM.
- Nonce: random 96 bits; nonce reuse under an epoch key is forbidden.
- AAD: canonical JSON with `version`, `board_id`, `epoch`, `record_id`,
  `record_type`, `author_pairwise_id`, `created_at`, and `policy_version`.
- Envelope carries `v=1`, algorithm, epoch, nonce, ciphertext, AAD fields, and
  tag. The existing signed content operation signs the complete envelope.

Attachments use a fresh random 256-bit attachment key, chunked AES-GCM with a
unique nonce per chunk. The attachment key is itself wrapped by the current
BEK. Filenames and media metadata live inside the encrypted manifest.

## Host protocol

The Host stores:

- board encryption mode and current epoch;
- BDK registrations bound to a valid board capability and policy version;
- wrapped epoch-key envelopes;
- encrypted content envelopes and minimal routing metadata.

The Host must reject plaintext content for an encrypted board and ciphertext
for a public/host-visible board. It never creates a BEK or accepts an unwrapped
BEK. All register/wrap/read/write endpoints require a short-lived,
board-scoped capability plus DPoP from the registered board device signing key.

## Membership, rotation, and recovery

- Adding a member/device does not expose old epochs by default. An explicit,
  separately audited history-sharing action is required to wrap older keys.
- Removing a member/device immediately increments the required epoch. Writes
  remain fail closed until an authorized administrator uploads the new epoch
  envelopes.
- A removed device may retain plaintext and old keys; UI states this clearly.
- A new device completes OID4VP again, generates its own board-scoped BDK, and
  requests an envelope. Another active authorized device approves and wraps
  the current epoch. The Host never performs recovery.
- Offline clients keep old local data and drafts. Publishing waits for a fresh
  capability and current epoch; stale-epoch writes are rejected, then locally
  re-encrypted after the new key is obtained.

## Privacy and logging

Logs and metrics may contain only aggregate counts, protocol versions, epoch
numbers, ciphertext sizes, and reason codes. They must not contain plaintext,
BEKs, KEKs, wrapped-key ciphertext, full device public keys, DIDs, VCs, VP
tokens, or notification previews.

## Required verification

- deterministic cross-platform vectors for ECDH/HKDF/AES-GCM and AAD;
- property tests for nonce uniqueness, tampering, wrong board/epoch/policy,
  stale writes, and unauthorized envelope retrieval;
- Relay/AppView contract tests proving plaintext/private metadata exclusion;
- multi-device join, removal, epoch rotation, offline draft, and recovery tests;
- external cryptographic review before changing the production feature gate.
