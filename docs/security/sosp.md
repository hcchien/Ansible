# Tris-Aura Strict Operational Security Policy

> Short name: SOSP  
> Status: Draft, required before public launch  
> Scope: App, Relay, AppView, P2P network, GCP operations  
> Goal: define the security checks that must pass before Tris-Aura goes live.

---

## 1. Data Privacy and Identity

### Passkeys Key Protection Policy

Private keys generated by Passkeys (WebAuthn) must remain in device hardware.

Requirements:

- iOS must store signing keys in Secure Enclave when available.
- Android must store signing keys in StrongBox / TEE when available.
- If hardware backing is unavailable, the App must clearly enter a
  reduced-trust mode rather than silently downgrading to software keys.
- Signing operations that create public Ops must require biometric confirmation
  (Face ID, Touch ID, or fingerprint unlock).
- Private key material must never be written to persistent storage outside the
  hardware enclave — not to SQLite, files, logs, analytics events, crash
  reports, photo libraries, clipboard, or screenshots.

Acceptance checks:

- [ ] Add platform capability detection for Secure Enclave / StrongBox / TEE.
- [ ] Require biometric confirmation before Lexicon record signing.
- [ ] Add tests for missing-hardware reduced-trust mode.
- [ ] Add static search checks for private key material in logs.

### DID Recovery Key Policy

DID key rotation and account recovery must not create a single point of failure.

Requirements:

- Implement Shamir's Secret Sharing for recovery material.
- Support 3–5 trusted recovery contacts.
- Require a threshold majority to recover identity.
- Recovery shares must not reveal the private key individually.

Acceptance checks:

- [ ] Define SSS share format and threshold policy.
- [ ] Add recovery flow threat model.
- [ ] Add tests proving fewer-than-threshold shares cannot recover identity.

## 2. Anti-Spam and Sybil Resistance

### Reputation Labeler

The AppView Labeler must maintain verifiable trust tiers for each DID.

Requirements:

- Basic (Passkey only): subject to the strictest rate limits.
- DNS Verified (custom Handle): DNS TXT or HTTPS `/.well-known/atproto-did`
  confirmed — allows higher rate limits and boosted sort weighting.
- Verified Human (future out-of-band verification): receives `✓` label in
  AppView rendering; least-restrictive rate limits.
- Labeler must never assign a higher tier without verified cryptographic proof
  of the underlying condition.

Acceptance checks:

- [ ] Define Labeler label fields aligned with `com.atproto.label.defs`.
- [ ] Add integration test: DNS-verified Handle → tier upgrade flow.
- [ ] Add integration test: label revocation on Handle DNS change.

### Anti-Spam (Rate Limiting and Proof of Work)

Because Passkey registration has low cost, the Relay must throttle unverified
accounts.

Requirements:

- Basic DIDs: Relay enforces rate limiting (configurable N Ops / minute).
- Relay MAY additionally require a Hashcash-style Proof of Work nonce attached
  to each `com.atproto.repo.createRecord` request from Basic DIDs.
- A single DID posting more than the configured threshold (e.g. 5 records / sec)
  must be temporarily suspended from further broadcasting on this node.
- Suspension must be reason-coded and time-bound; DNS-Verified and
  Verified Human DIDs have separate higher thresholds.

Acceptance checks:

- [x] Add DID-level Token Bucket rate limiter (carried over from v1.x).
- [ ] Define PoW nonce field in XRPC request extensions.
- [ ] Add tests for Basic DID suspension and automatic expiry.
- [ ] Add tests for DNS-Verified DID getting higher threshold.
- [ ] Add metrics for rate-limit decisions per tier.

## 3. Relay Op Encryption

Ops stored by the Relay must be encrypted at rest before they leave the trusted
client boundary (for private communities).

Requirements:

- App-generated Ops in private communities must be encrypted with
  user-controlled symmetric keys using AES-256-GCM.
- The Relay stores encrypted Op blobs and metadata required for routing,
  deduplication, and verification.
- Only authorized AppView nodes or user-authorized devices may hold
  decryption keys.
- Key distribution must be explicit and auditable.

Acceptance checks:

- [ ] Define encrypted Op envelope fields (see spec v2.0 §12).
- [ ] Ensure Relay storage never receives plaintext post content for encrypted
  communities.
- [ ] Add decrypt-authorized AppView test path and decrypt-denied negative tests.

## 4. AT Protocol Integrity

### Lexicon Signature Verification

Every Lexicon record entering the public forum must be verified.

Requirements:

- AppView must verify the Ed25519 signature over the CBOR-serialised record
  before folding into public views.
- Relay must reject any `createRecord` request whose `commit_sig` does not
  match the resolved DID public key.
- Signature and DID anchor must both be valid; expired or revoked DID entries
  must be treated as unverified.

Acceptance checks:

- [ ] Add Rustler batch verifier for AppView ingestion.
- [ ] Require both valid signature and non-expired DID anchor for public fold.
- [ ] Persist verification status and source DID provenance in rendered pages.

### MST Integrity

Content commits must be verifiable against their Merkle root.

Requirements:

- Relay must validate MST commit CIDs before accepting records.
- Duplicate CIDs must be rejected with `409 Conflict`.
- AppView must rebuild MST state from raw commits and confirm root CID matches
  before publishing rendered content.

Acceptance checks:

- [ ] Add duplicate-CID rejection tests in Relay.
- [ ] Add MST root verification step in AppView ingestion pipeline.

## 5. P2P Network Security

### Traffic Protection and Rate Limiting

The network must reject abuse without weakening privacy.

Requirements:

- TLS 1.3 must be used for all XRPC and WebSocket connections.
- Relay must enforce rate limiting for invalid records and high-frequency posting.
- Rate limiting must be reason-coded and time-bound.

Acceptance checks:

- [ ] Add malformed/invalid record rate limiter for peers.
- [ ] Add tests for automatic suspension expiry.
- [ ] Add metrics for rate-limit decisions.

### Log Redaction

Operational logs must not join identity and transport metadata.

Requirements:

- GCP Cloud Logging must not record direct IP-to-DID mappings.
- Request logs must redact DID values where IP or request path could identify a
  user transport route.
- Security logs may include reason-coded pseudonymous IDs, but must avoid raw
  keys, plaintext content, and direct IP/DID joins.

Acceptance checks:

- [ ] Add logging policy and redaction helpers.
- [ ] Add tests for no raw DID in request logs when IP metadata is present.
- [ ] Configure Cloud Logging sinks with retention and redaction rules.

## 6. Security Layer Components

### Comp A-1: Rust Memory Safety Module

Technology: `secrecy` or `zeroize`.

Responsibilities:

- Wrap signing key material in memory-safe secret types.
- Zero sensitive key buffers when keys are no longer in scope.
- Prevent accidental debug formatting of secret values.

## 7. Security Audit Lifecycle

| Phase | Security Task | Acceptance Standard |
|---|---|---|
| P1 Alpha | Verify Passkeys key isolation. | Private key cannot be extracted from Secure Enclave in any test path. |
| P2 Beta | Penetration test Relay XRPC endpoints. | Simulated replay and forged-signature attacks are rejected. |
| P3 RC | GCP infrastructure security scan. | IAM is least-privilege and GKE exposes no unnecessary public ports. |

Launch gate:

- [ ] P1 Passkeys key isolation test completed.
- [ ] P2 Relay penetration test completed.
- [ ] P3 GCP infrastructure scan completed.
- [ ] No known critical or high severity issue remains open.
- [ ] Incident response owner and rollback procedure documented.
